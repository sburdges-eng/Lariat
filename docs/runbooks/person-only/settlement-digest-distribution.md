## Steps
All steps on this Mac, one Terminal window, from the repo root.

2. **Render the default week through the job wrapper** (this is what cron would run; it leaves the audit row). `npm run job weekly-settlement-digest; echo "exit=$?"` → expect: one line `weekly-settlement-digest: YYYY-Www (YYYY-MM-DD..YYYY-MM-DD) — N show(s) → /Users/seanburdges/Library/Application Support/Lariat/data/exports/YYYY-Www_settlement.html` (`scripts/weekly-settlement-digest.mjs:156-158`) and `exit=0`. Exit 0 even when N=0 (`:19-21`). The wrapper spawns `npm run digest:settlement` with your environment (`scripts/run-job.mjs:140-144`), so the export in step 1 carries through. If `exit=75` (`already locked`): see "If something goes wrong". If `exit=1`: `tail -1 data/audit/job-failures.jsonl` (repo-relative, `run-job.mjs:44-46`) and stop.
   - *Catch-up for a specific week* (no `ingest_runs` row): `npm run digest:settlement -- --week-of=YYYY-MM-DD` — any date inside the target Mon→Sun week (`:47-48`). The `--` is required; without it npm eats the flag and the script prints `unknown arg` + help (`:39,135-140`, exit 64). ## Pass / fail
Per week, **handled** = all of: (1) `exports/YYYY-Www_settlement.html` exists for the week that ended last Sunday and step 2 exited 0; (2) no `data/lariat.db` in the repo after the run; (3) every show card in that week had a real deal and ticket lines before the PDF was saved, or the week had 0 shows and the digest says "No shows"; (4) the PDF is saved beside the HTML and sent to whoever settles; (5) `ingest_runs` has today's `job:weekly-settlement-digest` row with `status=ok` (skip for `--week-of` catch-ups).
**FAIL** = exit 1/64/75 from step 2, a stray repo `data/lariat.db`, a $0 card distributed, or a number edited by hand in the HTML/PDF. A FAIL never damages the live DB — the script only SELECTs (`weekly-settlement-digest.mjs:107-117`) and writes one HTML file (`:126-128`).

## If something goes wrong
- **`exit=75` / `already locked (held by pid …)`** (`run-job.mjs:120-124`): a previous run is still going or wedged. `npm run job:status weekly-settlement-digest` shows the holder; the lock is `$LARIAT_DATA_DIR/locks/weekly-settlement-digest.lock` (`lib/jobLock.ts:84`) and goes stale after 120 s (`scheduled-jobs.json:56`; `docs/JOBS.md:37-40`) — wait two minutes and rerun. Do not delete a lockfile whose pid is alive.
- **`exit=1` with `weekly-settlement-digest failed: SqliteError: no such table …`**: this checkout's schema does not match the live DB. Run from the checkout that serves the app and hand the error to an agent in chat. Do not run any migration script to "fix" it.
- **`unknown arg: --week-of=…` + help, exit 64**: you forgot the `--` after `npm run digest:settlement` (`:39,135-140`).
- **Stray `data/lariat.db` in the repo**: step 3. It is an empty, freshly-migrated DB, not a copy of anything; move it to `$TMPDIR` and fix the export. Never `cp` it over the live DB.
- **Wrong week rendered**: rerun with `--week-of=`. The HTML is replaced in place; a PDF you already saved is untouched — re-save it.
- **Numbers look wrong**: never edit the HTML or PDF. Fix the deal / box-office rows in the app and re-render. Settlement money math is a guarded surface (`docs/LARIAT_NATIVE_FINAL_AGENT_GUIDE.md:93`); an agent proposing a change to `lib/settlementRepo.ts` or `lib/settlementPrint.ts` needs a spec and review first.
- **Do not install the cron block to "automate" this today**: `examples/lariat.crontab:16-40` hardcodes `$HOME/Dev/Lariat` (`~/Dev` is the unmounted SSD), `scripts/cron-wrapper.sh:38,56` cd's to the repo and never exports `LARIAT_DATA_DIR`, so every job would open `<repo>/data/lariat.db` — an empty DB it creates itself. That fix is `install-lariat-cron-block` (no runbook file yet — `ls docs/runbooks/person-only/`), gated on `go-live-serving-topology-and-data-root.md:60-62`.
- Anything touching HACCP or a surface in `docs/PROTECTED_CONTRACTS.md` surfaces: stop and report in chat; this runbook never goes near them.
