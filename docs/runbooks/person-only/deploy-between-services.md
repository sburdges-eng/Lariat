## Steps
1. **Decide whether the range changes a board.** `git log --stat --oneline "$(jq -r .sha version.json)..origin/main" | grep -vE '^ (tests?/|docs/|scripts/|\.claude/|[^ ]*\.md)'` → the runtime files touched. Board-changing = anything under `app/`, `lib/`, `public/`, `middleware.js`, `package-lock.json`. If nothing prints: write the "No deploy" line (Record the result) and stop. If not sure what a diff does: `gh pr view <n>` and read the PR body — the seven gap-audit PRs said "between services" in their own row (`ORCHESTRATOR_STATUS.md:35-48`).
2. **Find the hub and how it was started.** `HUB=$(lsof -t -nP -iTCP:3000 -sTCP:LISTEN); ps -o pid=,ppid=,lstart=,command= -p $HUB; lsof -p $HUB | awk '$4=="cwd"{print $NF}'` → `next-server`, cwd `/Users/seanburdges/lariat_dev/Lariat`. 2026-09-02: PID 35362 is parented by a Claude Code session shell (35351 `npm run start` ← 35349 zsh ← 18621 `claude`), not a Terminal window — there is no window to Ctrl-C, and that session ending takes the hub with it. If cwd is anywhere else: stop and say so in chat — the served checkout is not this one and this runbook's paths are wrong for it.
3. **Back up the live DB.** `LARIAT_DATA_DIR="$HOME/Library/Application Support/Lariat/data" npm run backup` → `backups/<stamp>/SHA256SUMS` + `manifest.json`; then `npm run backup -- verify backups/<stamp>` → passes (`scripts/backup.mjs:14,22`). The env prefix is mandatory: scripts never read `.env.local` (no dotenv anywhere in `scripts/`), so without it `resolveDataDir()` backs up `<repo>/data` (`lib/dataDir.ts:33-35`). If verify fails: stop — do not deploy on a DB you cannot restore.
4. **Keep the running build for rollback.** `PREV="$HOME/lariat_dev/next-prev-$(cat .next/BUILD_ID)"; cp -R .next "$PREV" && cp version.json "$PREV/version.json" && du -sh "$PREV"` → ~526M copied. `next build` rewrites `.next` in place; this copy is the only rollback that needs no git.
5. **Fast-forward `main`.** `git status --short` (read it — the main checkout is shared, `CLAUDE.md:149-152`) then `git merge --ff-only origin/main` → `Fast-forward`. If it refuses naming files: they are another session's — `resolve-dirty-shared-main-checkout.md:20`; never `stash` or `reset --hard` (`CLAUDE.md:158-162`). If `package-lock.json` is in the range: `npm ci` (Node 24, `.nvmrc`); never `npm rebuild better-sqlite3` (`CLAUDE.md:99`).
6. **Stop the hub.** `kill $(lsof -t -nP -iTCP:3000 -sTCP:LISTEN); sleep 2; lsof -nP -iTCP:3000 -sTCP:LISTEN; echo stopped` → only `stopped`. Stop **before** building: `next start` opens `.next` files lazily (the hub holds no `.next` handles — `lsof`), so a rebuild under it serves a mix of two builds. This is the kill half of `npm run restart` (`package.json:52`) without the blind restart.
7. **Build.** `npm run build` → `prebuild` restamps `version.json` (`package.json:9-10`), then `✓ Compiled`; confirm `jq -r .sha version.json` = `git rev-parse --short origin/main`. If it fails: `rm -rf .next && cp -R "$PREV" .next && cp "$PREV/version.json" .` and go to step 8 — the old build runs fine on the fast-forwarded tree because `next start` serves `.next`, not source.
8. **Start it in a Terminal window you keep open.** `cd /Users/seanburdges/lariat_dev/Lariat && npm run start` (`= next start -H 0.0.0.0 -p 3000`, `package.json:51`) → `▲ Next.js 16.x` … `✓ Ready in …`. Never: `npm run dev`, `scripts/launch_lariat.sh` (`:14` kill -9 sweep, `:23` dev server), `scripts/Lariat Cockpit.command`, `scripts/install-prod-data.sh` (`:12` two writers). One writer on the WAL at a time — do not also open `LariatNative/build/Lariat.app`.
9. **Verify from a second terminal.** `curl -s localhost:3000/api/health | jq '{status,version}'` → `"ok"`; `curl -s localhost:3000/api/discover | jq -r .started_at` → just now; `lsof -p $(lsof -t -nP -iTCP:3000 -sTCP:LISTEN) | grep -c 'Application Support/Lariat/data/lariat.db'` → `≥1`; `ls data/lariat.db` → still `No such file` (the env took). Then on this Mac's browser open one board the range changed, **hard reload** (the service worker keeps `lariat-pages-v1` / `lariat-api-v1` until it re-activates — `public/sw.js:67-73,127,141`), and sign in with your PIN once (`go-live-pin-login.md`). If health is not `ok` or the board 500s: rollback (below).

## Pass / fail
No source defines deploy criteria; the nearest are the G0 rules (`2026-08-05-g0-gui-smoke-and-shutoff.md:137`: any operator-blocking surprise = FAIL) and the topology runbook's smoke checks.
**PASS** = all of: done outside a `service_hours` window with `0` established connections at stop; `jq -r .sha version.json` = `origin/main` tip; `/api/health` `ok`; hub holds the Application Support DB and no `data/lariat.db` appeared; one changed board renders after a hard reload; PIN login works; handoff line written.
**FAIL** = any of those missing, or a board error once service starts → rollback and log it.
**"Handled"** for this recurring task = one dated line in `.agent-sessions/handoff.md` per merged range: either the deploy record or `No deploy: <range> is docs/tests/tooling only`. A merged board-changing PR with no such line is an open instance.

## If something goes wrong
- **Build failed, or the new build misbehaves in step 9:** stop the hub (step 6), `rm -rf .next && cp -R "$PREV" .next && cp "$PREV/version.json" .`, `npm run start`. Leave the source tree fast-forwarded — `next start` serves `.next` only. If the range bumped `SCHEMA_VERSION`: also restore the DB — everything stopped (`lsof -nP -iTCP:3000` empty, `pgrep -lx Lariat` empty), replace `lariat.db` + `-wal` + `-shm` from `backups/<stamp>/` (`docs/OPERATIONS.md:101`).
- **Port 3000 busy on start:** `lsof -nP -iTCP:3000 -sTCP:LISTEN` and kill only that PID — never `scripts/launch_lariat.sh`'s sweep.
- **Boards empty after start:** wrong data root. Stop; `grep -n '^LARIAT_DATA_DIR=' .env.local` and `env | grep LARIAT` in the launching shell; fix or unset; start. Nothing was written to the live DB.
- **Service is starting and it is not up:** paper + the outage card (`docs/boh/print/outage-card.html`, from `go-live-print-pack.md`), roll back as above, and log it in `docs/superpowers/templates/service-day-shutoff-log.md` (G0 `:141`). Fix later, in a worktree, off the hub.
